## 四、发现的问题与风险

### 🔴 严重：无

### 🟡 中等

**M1: Canvas 不可见时缺乏降频机制**

- **位置**：`EnergyCanvas.tsx:208-369` rAF 循环
- **设计文档要求**（步骤 4，第 508-517 行）：Canvas 不可见时降至 2fps 检查（`setTimeout(() => renderLoop(), 500)`），节省 CPU
- **当前代码**：始终以 `requestAnimationFrame` 全速运行（60fps），无论标签页是否可见
- **影响**：标签页后台时持续消耗 CPU（Canvas 2D 每帧 clearRect + drawImage + stroke × 3），对电池续航有影响
- **建议修复**：添加 `document.visibilitychange` 监听或 `usePageVisibility` hook，不可见时跳过绘制逻辑

**M2: EnergyCanvas 数据追加逻辑内聚在 rAF 循环中，与 store 的 `consumeFrameFromBuffer` 存在数据耦合**

- **位置**：`EnergyCanvas.tsx:238-257` 数据追加 + `store.ts:177-235` consumeFrameFromBuffer
- **设计文档要求**（步骤 1，第 314-316 行）：使用 Zustand `subscribe` 监听 store 变化来采集数据（非 rAF 轮询）
- **当前代码**：EnergyCanvas 在 rAF 循环中通过 `getState()` 读取 store 并自行追加到 `bufferRef`。这引入了两处能量数据消费者的并行采集（store 的 `consumeFrameFromBuffer` 写入派生指标 + EnergyCanvas 从 store 读取追加 buffer），存在轻微时序差异
- **影响**：rAF 与 store 更新之间存在至多 1 帧的延迟（~16ms），对 60fps 渲染无视觉影响，但架构上数据采集逻辑分散在两处
- **建议修复**：考虑将 `energyBuffer` 的追加逻辑统一到 store 层（`consumeFrameFromBuffer` 发送事件或回调），或改为 `subscribe` 驱动，使数据采集与 UI 渲染解耦

### 🟢 轻微

**L1: `showComponents` 变更时不重建离屏图例**

- **位置**：`EnergyCanvas.tsx:194-204` useEffect 依赖数组
- **问题**：`showComponents` 不在 `redrawOffscreen` 的 useEffect 依赖中（仅在 mount 时绘制一次图例）。若运行时切换 `showComponents`，离屏 canvas 的 K/V 图例不会更新
- **影响**：低——`showComponents` 通常不运行时切换。即使切换，主 Canvas 的曲线绘制逻辑正确（会检查 `showComponents`），仅离屏图例可能不同步
- **建议修复**：将 `showComponents` 添加到 resize useEffect 的依赖数组

**L2: 颜色微调偏离设计文档**

- **位置**：`EnergyMonitorPanel.tsx:48-49` — 使用 `text-emerald-400` / `text-red-400`；设计文档要求 `text-emerald-500` / `text-red-500`
- **影响**：视觉差异极小（Tailwind 400 vs 500 色阶差约 10% 亮度）

### 总体评价

SIM-04 的落地质量高。设计文档中 7 个异常条件的精确处理全部在 `consumeFrameFromBuffer` 中实现（NaN 跳过+计数、阻尼豁免、阻尼变更基准重置、初始能量为零除零保护、reset 检测、锁存清除），11 个测试覆盖了全部状态机路径和边界条件。Canvas 渲染层使用离屏坐标轴 + 滑动窗口 + 降采样，架构避免了 D3 SVG 的性能陷阱。

主要改进点集中在 Canvas 不可见降频（节电）和架构上数据采集的订阅式解耦，均属优化而非功能缺失。
