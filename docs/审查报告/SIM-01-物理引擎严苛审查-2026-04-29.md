## 一、致命缺陷：批处理缓冲区覆盖导致"闪现"

### 问题定位

`scheduler.ts:267-268` — `handleWorkerMessage` 中 `batchReady` 分支

```typescript
case "batchReady": {
    this.currentBuffer = resp.buffer;   // ← 无条件覆盖旧缓冲区
    this.consumeIndex = 0;              // ← 无条件重置消费索引
    this.pendingBatch = false;
}
```

这是"偶发闪现"的**根因**。链路如下：

```
1. 批次 #0 在主线程消费到第 60 帧
   → consumeOneFrame 检测 consumeIndex(60) >= BATCH_PREFETCH_THRESHOLD(60)
   → requestNextBatch() → Worker 开始计算批次 #1

2. Worker 在 20~50ms 内完成 120 帧积分，postMessage batchReady(#1)

3. 主线程收到 batchReady(#1) 时，批次 #0 仅消费到 ~第 65 帧
   → 旧缓冲区还有 55 帧未消费

4. handleWorkerMessage 直接执行：
   this.currentBuffer = resp.buffer   // 旧缓冲区引用永久丢失
   this.consumeIndex = 0              // 消费进度被抹除

5. 下一帧 consumeOneFrame 从新缓冲区位 0 开始读取
   → 仿真时间从 t+65/60 跳到 t+120/60（跳变 ≈ 0.92 秒）
```

对于混沌双摆系统，0.92 秒的仿真时间差意味着李雅普诺夫指数发散后的完全不相干位置——摆球在屏幕上**瞬间闪现到另一个位置**。

**这不是偶发，是每个批次周期必然发生**（每 ~1 秒一次，取决于 Worker 计算速度）。

### 连带后果：缓冲区池泄漏

旧缓冲区的引用丢失后，永远不会调用 `this.pool.releaseBuffer()`。`Float64Pool` 仅有 10 个缓冲区（`float64-pool.ts:1`），~10 个批次循环后池耗尽，`acquire()` 返回 null，仿真**永久冻结**。

### 修复方向

需要在 `SimulationScheduler` 中引入双缓冲机制（`activeBuffer` / `nextBuffer`），仅在当前批次消费完毕时才切换：

```
batchReady 到达时：
  - 若 activeBuffer 存在且未消费完 → 存入 nextBuffer，不覆盖
  - consumeOneFrame 中消费完 activeBuffer 后 → 将 nextBuffer 提升为 activeBuffer
  - 每次切换时正确调用 pool.releaseBuffer 归还旧缓冲区
```

## 二、严重问题

### 2.1 积分器内存分配洪水

`integrators.ts:31-40` + `derivatives.ts:38`

每个 RK4 步骤产生 **7 个新 Float64Array(4)** 堆分配：

| 来源 | 每步分配 |
|---|---|
| `odeRhs()` 内部 `return new Float64Array([...])` × 4 次 | 4 |
| `addScaled()` 内部 `new Float64Array(4)` × 3 次（k2/k3/k4 中间态） | 3 |

每批次 120 帧 = **840 次小数组分配**。在 Worker 线程内触发 GC 暂停时，会延迟批次返回。虽然 Worker GC 不阻塞主线程，但批次延迟超过 1 秒（120-60 帧消费时间）时，即便双缓冲修复后也会出现消费端等不到数据的卡顿。

**修复方向**：使用预分配的 `Float64Array(4)` 工作缓冲区（类似 C 的栈变量），通过 `buf.set()` 写入而非 `new` 创建。`addScaled` 应接收输出参数而非返回新数组。

### 2.2 Velocity Verlet 错误应用于速度依赖系统

`integrators.ts:44-57`

Velocity Verlet 的辛性质要求加速度仅依赖位置：`a = a(x)`。双摆的角加速度依赖角速度的平方项（离心力/科里奥利力）：

```
α = f(θ₁, θ₂, ω₁², ω₂², ...)
```

代码中标准 VV 的半步速度-全步位置-重算加速度流程并未处理 `a = a(x, v)` 的情况：

```typescript
state[1] += 0.5 * dt * alpha0[0];  // v(t+½dt) 用 a(x(t))
state[0] += dt * state[1];         // x(t+dt) 用 v(t+½dt)
const alpha1 = angularAcceleration(state, p);  // a(x(t+dt)) — 应在 v(t+dt) 下计算！
state[1] += 0.5 * dt * alpha1[0];  // v(t+dt) 用 a(x(t+dt), v(t+½dt)) ← 速度不一致
```

实际效果：方法退化为精度不明的自定义格式。测试文件 `engine.test.ts:95-109` 的注释也打了预防针（"非天然辛积分器"），但仅验证 2 秒不发散——对于宣称支持 Velocity Verlet 的生产引擎而言，这种短时"不炸就行"的门槛过低。

**修复方向**：明确文档标注 Velocity Verlet 在速度依赖系统中的局限性，或改用迭代 Velocity Verlet（预估-校正循环），或替换为 RK4 作为唯一推荐积分器并将 VV 降级为实验性选项。

### 2.3 `tick()` 在无帧可消费时仍消耗时间预算

`Scene3D.tsx:422-428`

```typescript
while (simTimeAccRef.current >= dt && consumed < maxFrames) {
  scheduler.tick();                // ← 缓冲区为空时是空操作
  simTimeAccRef.current -= dt;     // ← 无条件扣减
  consumed++;                      // ← 无条件计数
}
```

当 `currentBuffer === null` 且 `pendingBatch === true` 时，`scheduler.tick()` → `consumeOneFrame()` 是空操作。但调用方仍扣减 `simTimeAccRef` 并消耗 `maxFrames` 预算。

后果：
- `simTimeAccRef` 变为负值，需要多轮 rAF 才能回到正值
- 插值因子 `alpha` 异常
- 当批处理间隙发生时，视觉上出现叠加的"时停"效果

**修复方向**：`tick()` / `consumeOneFrame()` 应返回布尔值表示是否实际消费了帧，调用方仅在返回 true 时扣减累加器。

## 三、中等问题

### 3.1 力数据缺少下摆球方向角

`ode-worker.ts:381-395` + `simulation.ts:66-79`

上摆球（ball 1）有 4 个力 × 2（大小+方向）= 8 个字段。下摆球（ball 2）仅有 4 个力的大小字段，**完全没有方向角**。

| 字段 | 上摆球 | 下摆球 |
|---|---|---|
| Fg (重力) | mag ✓ + angle ✓ | mag ✓, angle ✗ |
| T (张力) | mag ✓ + angle ✓ | mag ✓, angle ✗ |
| Fi_t (切向惯性力) | mag ✓ + angle ✓ | mag ✓, angle ✗ |
| Fi_n (法向惯性力) | mag ✓ + angle ✓ | mag ✓, angle ✗ |

`computeForceFrame` 甚至没有计算 ball 2 力的方向角。LAB-01 受力拆解视图的 ball 2 力矢量因此无法正确渲染。

**修复方向**：补全 `ForceField` 枚举和 `writeForceFrame`，在 `computeForceFrame` 中计算 ball 2 所有力的方向角。或将 `FORCE_STRIDE` 从 12 扩展到 20 以容纳完整数据。

### 3.2 `angularAcceleration` 冗余展开完整 ODE

`derivatives.ts:44-50`

```typescript
export function angularAcceleration(state, p): Float64Array {
  const rhs = odeRhs(state, { ...p, damping: 0 });  // 完整 RHS + 新参数对象
  return new Float64Array([rhs[1]!, rhs[3]!]);         // 再分配提取
}
```

展开了完整 ODE 计算（包括 ω₁、ω₂ 的恒等映射、α-damping 的零减法），仅为从中提取 α₁、α₂。每次调用多做了 50% 的无用计算，以及一次额外的参数对象分配。

**修复方向**：将角加速度的核心公式抽成独立纯函数 `computeAlphas(state, p)`，`odeRhs` 和 `angularAcceleration` 均调用它，避免冗余。

### 3.3 能量基线重置依赖脆弱的启发式判断

`store.ts:239-240`

```typescript
if (prev.t > 1.0 && currentT < 0.1) {
  // 判定为"新仿真启动"，重置能量基线
  ei = e; ed = 0; de = false; emin = e; emax = e; sa = true;
}
```

用 "前一帧 t > 1.0 且当前帧 t < 0.1" 判定新仿真启动是启发式 hack。如果参数热更新触发 Worker 内 `handleReset`（simTime 归零），但之前的 t 恰好 ≤ 1.0（如运行不到 1 秒就重置），则能量基线不会正确重置。

**修复方向**：使用 `resetTrigger` 计数器或显式的 generation ID 来标记仿真重置，而非依赖 simTime 区间判断。

### 3.4 模块级可变全局状态

`store.ts:22-23`

```typescript
let nanSkipCount = 0;      // 模块级可变变量
let lastDamping = NaN;     // 模块级可变变量
```

这两个变量位于 Zustand store 外部，是模块级可变状态。如果测试中创建多个 store 实例（或 store 被多次初始化），它们会跨实例共享，造成测试间的状态污染。

**修复方向**：将这两个变量移入 Zustand store 的 state 中，或使用 `useRef` 模式（如果必须在 React 外部）。

## 四、轻微问题

### 4.1 `safeDenom` 魔数缺乏论证

`derivatives.ts:21`

```typescript
const safeDenom = Math.abs(denom) < 1e-12
  ? (Math.sign(denom) || 1) * 1e-12
  : denom;
```

`1e-12` 作为硬编码阈值。对于极端参数组合（m1=1e-6, m2=1e-6, L1=3, L2=0.1），denom 在正常运行中可能接近这个量级，导致误触发保护而扭曲计算结果。此外 `Math.sign(0) || 1` 的兜底写法暗示作者意识到了 `Math.sign(0) === 0` 的陷阱，但条件分支已经包含了 `Math.abs(denom) < 1e-12`，进入该分支时 `denom` 几乎必然 ≠ 0，兜底几乎不会触发 —— 存在逻辑冗余。

### 4.2 `normalizeAngle` 浮点取模写法晦涩

`state-vector.ts:65`

```typescript
return ((angle + Math.PI) % (2 * Math.PI) + 2 * Math.PI) % (2 * Math.PI) - Math.PI;
```

JavaScript `%` 对负数的行为是"余数"而非"模"（`-0.5 % 6.283 !== 5.783`）。双次 `%` + `+ 2π` 的写法修复了这个问题，但可读性极差。此外对于 `angle = 1e16` 级别的极大值，`+ Math.PI` 会丢失于浮点精度中，使得归一化结果不正确（尽管这种角度在物理上不太可能出现）。

### 4.3 调度器零测试覆盖

现有的 27 个测试（`engine.test.ts`）全部针对引擎纯函数。`SimulationScheduler`、批处理缓冲区管理、Worker 消息协议、崩溃恢复、超时处理、池耗尽、双缓冲切换——所有这些**零覆盖**。这是本次审查中最严重的测试缺口。

### 4.4 仿真暂停时累加器过早清零

`Scene3D.tsx:428-430`

```typescript
} else {
  simTimeAccRef.current = 0;  // 暂停时清零
}
```

仿真暂停时将累加器清零，意味着恢复后的第一帧 `alpha` 必为 0（`isEffectivelyStopped` 路径），失去平滑过渡。应保留累加值以便恢复时插值连贯。

### 4.5 Velocity Verlet 每个半步都通过 `odeRhs` 获取加速度

`integrators.ts:45,53` — 两次调用 `angularAcceleration(state, p)`

`angularAcceleration` 内部调用 `odeRhs`（完整 RHS），然后 Velocity Verlet 的两个半步各调用一次。若后续修复了 3.2 的冗余计算，此处也自然受益。

## 五、积分器数值精度分析

### RK4（默认）

方程实现已验证与标准拉格朗日推导一致（`delta = θ₂-θ₁` 约定下）。主要精度瓶颈来自 4.1 中的 `safeDenom` 保护阈值。

测试表明 600 步（10 秒 @60fps）能量漂移 < 0.5%——在无阻尼情况下可接受。更长时间（如 6000 步=100s）的漂移行为未经测试。

### 能量计算中的势能参考点

`state-vector.ts:45`:
```
V = m1*g*y1 + m2*g*y2
```

其中 `y1 = -L1*cos(θ1)`, `y2 = y1 - L2*cos(θ2)`。y↑ 为正（物理约定），y=0 为支点高度。势能零参考点取在支点，因此 pendulum 自然下垂时 V < 0（合理）。但 `engine.test.ts:143-148` 的测试仅验证 "能量值有限 " 而未验证其数值正确性。
